# Production row-level security rehearsal

This is a design rehearsal, not a production migration. On 5 November 2026 the live `crunchify_private` tables still had row-level security disabled. Their direct grants denied `anon`, `authenticated`, `service_role` and the restricted preview role access, but the legacy broad credential and owner privileges remain separate risks. The hosted database reports PostgreSQL 17.11; this rehearsal used an isolated local PostgreSQL 18 cluster containing only synthetic data.

The test-only SQL is [rls-rehearsal.sql](../../web/tests/fixtures/rls-rehearsal.sql). It gives the restricted production application role read policies on all five tables, insert policies for inquiries, rate limits, history and sessions, update policies for inquiries and rate limits, and a delete policy for sessions. It gives the restricted backup role read policies. Existing SQL grants remain necessary: policies do not grant table privileges. The policies grant those application roles access to all permitted rows; they are not per-staff or per-inquiry isolation. A database owner or bypass-RLS role can bypass these policies, so the older broad credential still needs an owner-approved rotation and retirement plan.

## Rehearsal results

- With RLS enabled on the five local tables, the non-superuser application role could read products, create and update a synthetic inquiry, create its history entry, update the rate limit and create/delete a session. A browser test against that role exercised wholesale and partner submissions, admin sign-in, update, retry and sign-out using synthetic data and disabled email.
- A separately created test role with schema and table SELECT grants but no matching policies saw zero rows. The preview role still lacked production-schema usage. These checks were local; they do not prove the live system's behavior after a policy change.
- The existing restricted-role `pg_dump` command failed when it encountered RLS, rather than silently producing a backup. A separate test used `--enable-row-security --inserts` and restored a synthetic archive whose owner and backup-role counts matched across all five tables: 4 products, 1 inquiry, 1 history entry, 6 rate-limit rows and 3 sessions. The disposable databases and synthetic dumps were removed afterward.
- A second [GitHub Actions rehearsal](https://github.com/Lester0961/crunchify-trial/actions/runs/41953425058) passed using a disposable PostgreSQL 17 container, matching the hosted major version. The containerized app used a non-superuser application role; it saved a synthetic wholesale inquiry, authenticated staff, updated the inquiry and history, and revoked a copied session. A granted test role without a policy saw no products. The ordinary dump failed as expected; a separate policy-aware synthetic export restored with counts matching both the owner and backup role. Email was disabled, and this does not establish production backup completeness or exact hosted patch-level behavior.

**Do not switch the live backup to `--enable-row-security` merely to make the dump succeed.** It exports only rows visible to the backup role. Missing or restrictive policies could silently produce an incomplete backup. A production design must independently verify complete coverage using an approved trusted method and a consistent database snapshot, fail closed on policy drift, encrypt and store the result off-device, and successfully rehearse restoration. Recreate grants and invalidate restored sessions as described in [BACKUP-RESTORE.md](../BACKUP-RESTORE.md).

Before any live migration, agree the role/policy model and backup ownership with the company, test against a separately isolated PostgreSQL 17 staging environment with the actual application and backup tools, verify owner and backup counts under a consistent snapshot, test all read/write and denied-access paths, and document rollback. Apply only a reviewed, versioned migration during an approved window after a verified backup and restore. This rehearsal did not change production RLS or retire any credentials.
